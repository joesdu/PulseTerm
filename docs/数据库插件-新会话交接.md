## 二、先读这一节：会浪费你时间的坑

这几条每一条我都真踩过，按被坑的概率排序。

1. **`python3` 是 Windows 应用商店的占位程序，会静默什么都不做。**
   用 `python`（3.12.4）。用错了脚本不报错、也不生效 —— 我因此丢过好几轮编辑。
   **每次脚本化编辑之后都 `grep` 一遍确认内容真的进去了。**

2. **`dotnet` 命令要 `dangerouslyDisableSandbox: true`** —— 沙箱会挡住 NuGet restore。

3. **heredoc（`cat > file <<'EOF'`）在复杂内容上会炸**（`unexpected EOF while looking for matching`）。
   大段内容一律用 Write 工具落文件，再 `python <文件>` 执行。

4. **VelaShell.exe 正在运行时会锁住插件 dll**，构建报
   `文件被 VelaShell (pid) 锁定`。先 `Stop-Process -Name VelaShell -Force`。

5. **增量构建会把警告藏起来。** 只改了几个文件时 MSBuild 不重编其余项目，警告就不重发。
   **验收警告数一律用 `dotnet build VelaShell.slnx -c Debug --no-incremental`** ——
   实测普通构建报 0 警告、加上这个开关炸出 7 条。

6. **不要 stop/rm 那四个数据库实例**（见第三节），它们是共享的真机测试环境。

   **也不要往 `ops_pg` 里加建删表的用例。** 那个库是 `PostgreSqlOpsTests` 与
   `PgBinaryFallbackTests` 共用的，而后者的 `select * from pg_class limit 20`
   **靠物理行序取样** —— 你在同一个库里建删一张表就可能把它取到的 20 行换成
   `relacl` 全为 NULL 的那批，于是它不再触发文本降级、断言落空，
   而报错完全指不到你身上。要建删就开自己的库（`SqlCrossCatalogTests` 用的是 `cross_pg`）。

7. **headless 用例的断言会被静默吞掉。**
   `HeadlessUnitTestSession` 没有 `Func<Task>` 重载，不返回值的 `async` lambda 被绑到
   `Action` 上变成 `async void` —— 断言异常没人接，**测试恒绿**。
   写 headless 用例时 lambda 末尾**必须** `return true;`。
   已有 `HeadlessDispatchGuardTests` 扫源码守着，但你自己写的时候要知道为什么。

8. **`Loc` 对不认识的键原样返回键名**，所以漏加文案键的表现是**界面上出现一行 `Sql_XxxYyy`**，
   而中英键集一致性检查照样绿（两张表同时缺同一个键）。
   已有 `SqlContractTests.文案表_源码里取过的键一个都不能少` 扫源码守着。

9. **新引入任何测试脚手架，第一件事是往里塞一句 `Assert.Fail`，确认它真的会红。**
   这条是上面第 7 点的教训 —— 成本三十秒，那次省下的是八条「以为验过、其实没验」的用例。

## 五、别推翻这些决定

每一条都是被真机推翻过初版之后才定下来的。

1. **SqlSugar 只做驱动装配与元数据兜底，不做引擎。**
   元数据一律直查系统表，一个 `IDbMaintenance` 方法都不调 ——
   实测 `IsIdentity` 在 PG/MSSQL/MySQL 上**对每一列都返回 True** 并污染缓存，视图拿不到列，
   跨 schema 同名表会串。

2. **方言包与执行层不引用任何驱动类型。** 需要驱动特有属性时**用反射**，拿不到就当没这回事。
   已有两处先例：`OraclePack.EnableLongFetch`（`InitialLONGFetchSize`）、
   `SqlExecutor` 的 PG 文本回落（`AllResultTypesAreUnknown`）。

3. **元数据连接必须走 `SqlConnection.UseAsync` 排队。**
   Npgsql / MySqlConnector 不允许一条连接上并发跑命令，而对象树的展开是即发即忘的、
   天然会并发。直接摸 `.Raw` 就绕过了闸门。

4. **一个「数据库」页签 + 五个变体**，不是五个页签。
   端口 / 主机标签 / 要不要凭据由 `WorkspaceDescriptor.Variants` 承载。
   **加新语义时要把「谁在读它」全找出来** —— 变体上线时就漏了两处
   （表单装载路径、连接时的凭据判定），表现是「明明没让我填，连的时候却非要我填」。

5. **写操作三档护栏**，判据按**括号深度**分词。
   `WITH x AS (SELECT…) DELETE` 的真动词、`UPDATE t SET a=(SELECT…WHERE…)` 这种无界更新，
   只有深度感知才判得对。

6. **方言给不了的时候要说出来，不能留空白。**
   空白与「这张表真的没有索引」「现在真的没人连」长得一模一样。
   **但"这个方言压根没有这一类对象"是另一回事** —— 给 MySQL 画一个恒空的「序列」分类，
   与「这个库真的没有序列」长得一模一样，所以能力位（`HasSequences` / `HasRoutines`）
   为 false 时整个分类不画。

7. **系统对象走 `SqlObject.IsSystem`，永不借道 `Comment`。**
   上一版把它写进 `Comment` 里的一个 `"@system"` 记号，指望对象树认 —— 而树一个字都没读，
   于是 Oracle 根上 28 个系统 schema 与 2 个用户 schema 混排。
   `OraclePackTests.系统对象的标记不再借道注释字段` 扫源码守着这条。
   配套：系统对象**列出来但归组**，不是滤掉 —— `msdb.dbo.backupset`、`sqlite_sequence`、
   `pg_class` 都是有人真要查的。

8. **树上的每个节点都要带自己在哪个库（`SqlTreeNode.Database`）。**
   PG / SQL Server 的目录表每库一份，而两段限定名说不出"哪个库" ——
   库这一级只能落在**连接**上（`SqlSession.MetadataForAsync`）。
   缺这一格的直接后果就是"每个库都点得开、每个库都是空的"。
   **加新的元数据入口时要把这一格传下去**，漏了不会编译失败,只会查到别的库。

9. **元数据查询一律经 `SqlConnection.UseAsync`，任何地方都不许直接摸 `.Raw` 发命令。**
   这条第 3 点已经写过一次，而结构页与运维面仍然有 5 处直接
   `_session.Metadata.Raw.CreateCommand()` —— 已全部改掉。
   撞上的表现是 `A command is already in progress`，而它看起来像"这条 DDL 有问题"。

## 六、已验证 vs 仍然欠着

**已在真机验过**（每条都有用例）：五方言连通、元数据逐项对账（类型原文/自增/生成列/默认值/
索引唯一性/外键/视图的列/跨 schema 不串）、分页、取消、就地写回与乐观并发、
结构页、表设计器四条 DDL、执行计划、会话与锁、导出编码、宿主整链路装载。

**对象树返工那一轮补的真机验收**（`SqlCrossCatalogTests` / `SqlTreeGuardTests`）：
连在 A 库看得见 B 库的表（PG + SQL Server）、系统库与系统 schema 各归各的（PG + SQL Server）、
例程与序列各有分类且不含 identity 内部序列（PG / MySQL / Oracle）、
表与视图共用一次清单查询、过滤实时生效、F5 真的重查。

**仍然欠着**：

- **触发器这一类还没接上**。模型里有 `SqlObjectKind.Trigger`，
  `PostgreSqlPack.ListTriggersAsync` 也已写好（含 `NOT tgisinternal` 那条关键过滤），
  但 `IDialectPack` 的契约没开这一格，另外四个方言也没写。Navicat 有这一栏。
- **例程 / 序列只列得出来，点不开**。看不到定义源码、参数、序列当前值 ——
  「列得出来」与「用得上」之间还差一页。
- **树上不能建 / 删对象**。右键仍只有「打开数据」「查看结构」两项。
- **一个库几千张表时的表现没实测**。过滤时 `_all` → `Children` 是 O(n) 全量重建，
  本机最大的数据集只有 9 张表，那条路等于没跑过。
- **PG 10 及以下的例程回落路径未验证**（`proisagg` / `proiswindow`），
  SQL Server 2008 R2 以下 `sys.sequences` 缺失的回落同样未验证 —— 手上只有新版服务端。
- **Telnet 的 `Write_AfterServerTakesOverEcho_DoesNotEchoLocally` 在全量跑时会红**（单独跑
  该程序集 24/24 全绿）。**与数据库插件无关，本轮没有碰它**，但根因已经抓到了，记在这里省下一次排查：

  ```
  expected: "X"
  actual:   "ls"        ← 本地把 "ls" 回显出来了
  ```

  用例先让对端发 `WILL ECHO`，再 `WaitForBytesAsync([255,253,1])` 等客户端回 `DO ECHO`，
  然后才写 `"ls"`。而 `WaitForBytesAsync` 是在**服务端收到 DO ECHO 的那一刻**返回的 ——
  如果客户端是「先把 DO ECHO 写出去、再置上"对端接管回显"这个标志」，
  中间就有一个窗口。机器空闲时窗口小到测不出来，全量跑挤满 CPU 时就漏出来了。
  修法多半是**把置标志挪到发回复之前**（一行），但那是 Telnet 侧的判断，
  要连它的协商状态机一起看，不该顺手改。

- **本插件的 `SqlEndToEndTests.SQLite_取消跑飞的查询` 也只在全量跑时红**
  （单独跑插件 249/249，连跑多遍全绿）：

  ```
  SQLite 应当在第一档就被 sqlite3_interrupt 打断。
  expected: DriverCancel
  actual:   Abandoned
  ```

  取消阶梯的第一档给 `sqlite3_interrupt` 的宽限是
  `SqlCancellation.DriverCancelGrace = 1500ms`。机器空闲时递归 CTE 被打断只要几十毫秒；
  Redis / AI 那两组把 CPU 跑满时，那条查询线程要更久才轮得到去看中断标志，
  于是超出宽限、阶梯升级到"放弃引用"。**产品行为是对的**（阶梯本来就是为这种情况设计的），
  是用例把"必须停在第一档"钉得太死。

  **本轮没有改它**：`DriverCancelGrace` 是一个 UX 取值（用户按下取消之后多久开始升级），
  为了让一条用例在满载机器上变绿去调它是本末倒置。要动的话该动的是用例 ——
  让它接受"查询确实很快停了、只是阶梯报了更高一档"这种结果。

- **Oracle `CANCEL SQL` 在 12c / 11g 上** —— 26ai 上验过生效（`ORA-01013`，且连接仍可用），
  老版本会不会 `ORA-00933` 没有实例可验。
- **降序索引的列名形态**（Oracle）、`IsAutoToUpper` 那条大小写陷阱。
- **宿主 `StandaloneSftpDocumentBehaviorTests` 的 4 条用例是死锁的** ——
  占着 UI 线程去 `await` 需要 UI 线程的任务。**刻意没修**：重构它们的等待方式是宿主侧的活，
  改错了会掩盖真实线程行为。已在 `HeadlessDispatchGuardTests.KnownInert` 记成棘轮：
  名单里的可以先欠，**名单之外一处都不许新增**；欠账清掉之后要连名单一起删。
- **国产库与同族方言**（达梦 / 人大金仓 / TiDB / OceanBase / openGauss 等）一个都没测。
- **性能数字全部来自本机回环**，没有真实网络延迟。
- **PG 降级取数的代价**：全文本格式下 `bytea` 会丢掉网格里的二进制标记
  （类型名与 NULL 判定不受影响）。

| # | 操作 | 合格标准 |

| # | 操作 | 合格标准 |
|---|---|---|

## 九、常用命令

```bash
# 全量测试(约 5 分钟)
dotnet test VelaShell.slnx -c Debug

# 只跑插件
dotnet test tests/VelaShell.Plugin.Sql.Tests/VelaShell.Plugin.Sql.Tests.csproj -c Debug

# 验收警告数(必须用 --no-incremental,否则数字不可信)
dotnet build VelaShell.slnx -c Debug --no-incremental

# 量发布包(24 MB / 43 文件,无 runtimes/ 树)
dotnet publish src/VelaShell/VelaShell.csproj -c Debug -r win-x64 --self-contained false -o <目录>

# 起应用(先确认没有旧进程锁着 dll)
Stop-Process -Name VelaShell -Force -ErrorAction SilentlyContinue
src/VelaShell/bin/Debug/net11.0/VelaShell.exe
```

**Release 发布跑不通**：缺 `src/VelaShell.snk`（一个不在仓库里的密钥），这是既有欠账，与本插件无关。
