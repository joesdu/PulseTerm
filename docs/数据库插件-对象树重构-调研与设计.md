# 数据库插件 · 对象树重构 —— 调研与设计

> 这一轮的起点是两句用户原话：
> **「数据库实例下的系统表和用户表混在一起根本没法用」**、
> **「pgsql 数据库连表都显示不出来」**。
>
> 两句都属实，而且根因不同。往下查还带出另外五处 —— 其中两处会让应用崩掉或挂死。
>
> 前作：`SqlSugar数据库管理插件调研与设计.md`（为什么这样建模）。这一份是**对象树这一块的返工记录**。
>
> 日期：2026-08-21。所有数字都来自四台本机真机：PostgreSQL 18.1、MySQL 8.4.11、
> SQL Server 2025 (LocalDB)、Oracle 26ai Free 23.26.2，外加 SQLite。
> 真机的起法与连接参数见 `SqlSugar数据库管理插件调研与设计.md` 附录 A。

## 一、两条主诉的复现与根因

### 1.1 「系统表和用户表混在一起」

**属实，而且是整棵树的第一层就混。** 真机计数：

| 方言 | 第一层节点 | 其中系统的 |
|---|---|---|
| Oracle 26ai | 30 个 schema | **28**（`ORACLE_MAINTAINED='Y'`） |
| MySQL 8.4 | 14 个库 | 4（`information_schema`/`mysql`/`performance_schema`/`sys`） |
| SQL Server 2025 | 全部库 | 4（`database_id ≤ 4`）+ 每库十来个系统 schema |
| PostgreSQL 18.1 | 全部库 | `postgres` + 每库的 `pg_catalog`/`information_schema` |

Oracle 那一栏尤其致命：用户的两个 schema 被 28 个 `SYS*` 埋在字母序中间。

**根因不在方言包，在于一条从没有人接通的线。** 五个方言包都算出了"这是不是系统对象",
然后把结果写进 `SqlObject.Comment` 的一个 `"@system"` 字符串记号里。
`MySqlPack` 上的注释原文是：

> 系统库的记号，写进 `SqlObject.Comment`，**对象树认它来决定默认折叠**。

而对象树**一个字都没读**。`SqlTreeViewModel` 里搜不到 `@system`、搜不到 `Comment`。
`SqlServerPack` 与 `OraclePack` 还特意把常量别名指到 `MySqlPack.SystemDatabaseMarker`，
配了一条单测守"三个包的记号必须同值" —— 一条守着三个**谁都没在用**的常量的用例。

顺带的第二重伤：`Comment` 是要显示给用户的字段。于是系统库的"注释"就是 `@system` 这四个字。

**这类缺陷值得单独记一笔**：它不是逻辑写错，是一条**约定的两端只做了一端**,
而做了的那一端注释写得非常笃定。编译器管不着，单测（守常量同值的那条）还是绿的。

### 1.2 「pgsql 数据库连表都显示不出来」

**属实。** 复现路径：连 PostgreSQL 时"数据库"栏留空（表单提示原文是
"留空则列出你能看见的每一个库"),Npgsql 落到 `postgres` 库。树上如实列出 12 个库，
每一个都点得开，**每一个点开都是一个空的 `public`**。

真机实证（psql,同一条 SQL 换库跑）：

```
连到 postgres:  SELECT relname FROM pg_class ... WHERE nspname='public'  →  0 行
连到 ops_pg:    同一条                                                   →  9 行
```

**根因**：PG 的目录表只覆盖当前连接所在的那个库，而 `SqlTreeViewModel` 对**每一个**库节点
都拿会话上那条唯一的元数据连接去查：

```csharp
// 旧代码。node.Target.Name(就是被展开的那个库)整个没有被用到。
private async Task<IReadOnlyList<SqlTreeNode>> LoadUnderDatabaseAsync(SqlTreeNode node, ...)
{
    IReadOnlyList<SqlObject> schemas = await _session.Metadata
        .UseAsync(_session.Pack.ListSchemasAsync, token);   // ← 查的永远是连接串里那个库
    ...
}
```

MySQL 侥幸没事：`information_schema` 是服务端级的，`TABLE_SCHEMA` 只是一列过滤条件。
**SQL Server 与 PG 同病**：`sys.objects` / `sys.schemas` 也是每库一份。

模型上缺的那一格是：**"库"这一级无法用限定名表达**。两段限定名只到 schema,
所以库只能落在**连接**上 —— 而当时的会话只有一条元数据连接。

## 二、顺带查出来的另外五处

按严重度排。

| # | 问题 | 后果 |
|---|---|---|
| 1 | `SqlWorkspaceViewModel.OpenData` 是 `async void`，里面 `await` 一条元数据查询 | 那条查询一抛（库不可达 / 权限不够），异常落到同步上下文 —— 在 Avalonia 里就是**整个应用崩掉**,而用户做的只是双击了一张表 |
| 2 | 结构页 3 处、运维面 2 处直接 `_session.Metadata.Raw.CreateCommand()` | **绕过了连接上的"一次只跑一条"闸门**。树的展开是即发即忘的，与结构页的 DDL 撞上就是 `A command is already in progress` —— 而它看起来像"这条 DDL 有问题" |
| 3 | 「表」与「视图」两个分类各调一次 `ListRelationsAsync` | 方言包刻意做成一次查完（§7.2 的计数要求），被树白白浪费掉。几千张表的库上多出来的那一遍是实打实的一秒 |
| 4 | 过滤词只在**装载那一刻**参与一句 `Where` | 改过滤词对已经展开的节点毫无反应。**一个不起作用的输入框比没有更坏** |
| 5 | 树上只有「表」「视图」两栏 | `SqlObjectKind` 上的 `Procedure`/`Function`/`Sequence`/`Trigger` 四格从建模那天起就没有人填过。对标 Navicat 这是硬缺口 |

另外记两处**刻意保留**的：
`SqlServerPack` 主机含 `\` 或以 `(local` 开头时不拼端口、用户名为空走集成认证 —— 那是 LocalDB,不是 bug。

## 三、设计

### 3.1 系统性进模型：`SqlObject.IsSystem`

```csharp
internal sealed record SqlObject(
    SqlObjectKind Kind, string Name, string Schema = "", string Comment = "",
    long? EstimatedRows = null, bool IsSystem = false);   // ← 新的一格
```

三条配套决定：

1. **`Comment` 让回给注释。** 三个 `@system` 常量连同守它们同值的那条单测一起删掉，
   换成一条**扫源码**的棘轮：方言包里不许再出现 `"@system"` 字面量
   （`OraclePackTests.系统对象的标记不再借道注释字段`）。扫源码是因为这类回退不会以编译错误的形式出现。

2. **判据一律由服务端回答，写成 SQL 表达式。**
   PG 的 `SystemSchemaExpr`、SQL Server 的 `SystemObjectExpr` 各只写一份，
   `ListSchemas` / `ListRelations` / `ListRoutines` 共用 —— 两处各写一份的话，
   迟早有一处漏掉 `information_schema`，表现是"大部分都归好类了，唯独这一个混着"。

3. **系统性可以从父节点继承。** Oracle 的关系清单不带这一格（要多 join 一次 `ALL_USERS`），
   但它的 schema 带 —— 树把父节点的系统性往下传。两条通道是**并集**,不是二选一：
   SQL Server 上 `msdb` 是系统库（继承管得着），而用户库里的 `sysdiagrams` 是
   `is_ms_shipped=0` 的工具产物（只有逐对象判据管得着）。

### 3.2 从"滤掉"改成"标出来"

原先四个包里有三处是拿 `WHERE` 把系统对象整个排掉的。全部改成标记：

| 原先被排掉的 | 现在 | 为什么要它 |
|---|---|---|
| SQL Server `is_ms_shipped = 1` | 标记 | `msdb.dbo.backupset`、`msdb.dbo.sysjobs` —— **运维每天都要查**,而它们全是 ms_shipped |
| PG `pg_catalog` / `information_schema` | 标记 | "看看 `pg_class` 长什么样"原先根本做不到 |
| SQLite `sqlite\_%` | 标记 | `sqlite_sequence` 是查 AUTOINCREMENT 位点的**唯一**途径 |

仍然排掉的只有真正的**会话内临时物**：PG 的 `pg_temp_N` / `pg_toast*`。
它们的个数随会话变，列出来是噪声不是信息。

**同一条判据的另一面**：引擎为 identity 列自建的序列**不算序列** ——
Oracle 的 `ISEQ$$_74207`（`ALL_OBJECTS.GENERATED='Y'`）、
PG 的 `pg_depend.deptype='i'` 那批。用户删不掉也改不动，画出来就是一个点了没用的节点。
真机上 `velaspike` schema 的三条序列里两条是这种，`ops_pg` 的四条里两条。

### 3.3 树上的归并规则

```
ops_pg                     ← 用户库在前
  public                   ← 当前 schema 加粗
    表 (9)
      orders
      系统对象 (2)         ← 同级最后,折叠
    视图 (0)
    存储过程与函数
    序列 (2)
  app
  系统对象 (2)             ← pg_catalog / information_schema
系统对象 (1)               ← postgres
```

`Group(nodes, parentIsSystem)` 的三条边界都是刻意的：

- 父节点本身就是系统的（`pg_catalog` 下的表）→ **不再套一层**,里面全是系统对象;
- 一个系统对象都没有 → 不画空分组;
- 全都是系统对象 → 平铺。这一层里没有"混排"这回事。

分组节点**建的时候子节点就已经在手上**（与外面那批是同一次查询的结果），
所以它不挂加载器、直接算"已装载" —— 过滤才穿得透它，计数才说得出来。

### 3.4 按库的元数据连接

新增方言能力位：

```csharp
/// 一条连接的元数据查询能不能看见别的库。
bool MetadataSpansCatalogs { get; }
```

| 方言 | 取值 | 依据 |
|---|---|---|
| MySQL | true | `information_schema` 是服务端级 |
| Oracle | true | 本包压根不画"库"这一级 |
| SQLite | true | 只有一个库 |
| **PostgreSQL** | **false** | `pg_class` 每库一份，且 PG 没有三段名 |
| **SQL Server** | **false** | `sys.objects` 每库一份 |

**默认写成 `true` 是刻意的**：不能跨是少数派，而且一旦漏覆盖，表现是"树上全是空库",
真机上一眼就看得见;反过来默认写 `false` 的话，漏覆盖的方言会白开一堆连接而照样能用 ——
那种错没人会发现。

`SqlSession.MetadataForAsync(database)` 按库懒开并缓存。两个细节：

- **`Lazy<Task<T>>` 而不是 `GetOrAdd` 一个 `Task`**：`GetOrAdd` 的工厂在并发下可能被调用多次，
  输的那次会开出一条没人持有、也没人关的连接。树的展开是即发即忘的，这不是理论风险。
- **连接用 `CancellationToken.None` 建立**,调用方的取消只作用在 `WaitAsync` 上。
  缓存里那个 `Task` 是所有人共享的 —— 让第一个调用方的取消把它变成 canceled,
  后面每一个人都会拿到一条永远连不上的连接。取消该做的是"我不等了",不是"谁都别想连"。

**SQL Server 为什么不用三段名**（`[db].sys.objects`，理论上跨得过去）：
那要求把库名拼进 SQL —— 参数化不了，那是对象名的位置。
于是每条元数据查询都多一处"用户标识符进 SQL"的入口，而本包的纪律是永不拼用户标识符
（§5.4.4 那条实测能删表的教训）。按库开连接反倒更省事，还与 PG 共用同一套机制。

**查询标签也要带库。** 双击 `ops_pg.public.orders` 生成的是 `SELECT * FROM "public"."orders"`，
两段名说不出"哪个库" —— 标签绑在节点所在的库上，并在底栏画一个「位于 ops_pg」的徽标，
因为用户没有第二个途径知道这件事。

### 3.5 缓存：一次查询喂多个分类

`(桶, 库, schema) → Lazy<Task<清单>>`，「表」与「视图」共用一个桶。

缓存键**用记录不用拼字符串** —— 这一条是现场付过学费的：第一版键拼的是
`桶\0库\0schema`，而作废那一侧按 `" 库 schema"` 去后缀匹配，两处分隔符不同，
F5 于是清不掉任何一条。编译期看不出来、运行期不报错，表现只是"F5 没反应",
**而用户会据此认定"库里真的没有那张新表"**。记录的相等性由编译器生成，没有分隔符这回事。

配套：`SqlTreeViewModel.RefreshAsync(node)` 先作废该 (库, schema) 下全部类别再重载。
F5 必须真的重查，这条由 `SqlTreeGuardTests.F5要真的重查而不是拿回缓存` 钉住
（它当场抓到了上面那个分隔符缺陷）。

`MetadataQueries` 计数器是为了让"表与视图共用一次查询"可断言 ——
这件事没有任何外部表征：两边都出数、都对，只是系统表被查了两遍。

### 3.6 过滤

节点存两份：`_all`（未过滤）与 `Children`（可见投影）。过滤词变化时自顶向下推、
自底向上投影。规则：

- **只有对象叶子参与名字匹配**（表/视图/物化视图/过程/函数/序列）。
  用户敲 `order` 是想找 `orders` 表，不是想让"表"这个分类消失。
- 容器的去留由"筛完还剩不剩东西"决定，但**没展开过的容器一律留着** ——
  里面有什么还没查过，凭什么说它不匹配。

过滤词挂在**节点实例**上而不是静态字段：一个 VelaShell 里可以同时开着几条数据库连接，
静态字段会让 A 连接的过滤词悄悄作用到 B 连接的树上，而那种串扰只在两个文档同时开着时出现。

### 3.7 新对象类别

`IDialectPack` 加两个方法 + 两个能力位：

```csharp
bool HasRoutines { get; }     bool HasSequences { get; }
Task<IReadOnlyList<SqlObject>> ListRoutinesAsync(conn, schema, ct);
Task<IReadOnlyList<SqlObject>> ListSequencesAsync(conn, schema, ct);
```

| 方言 | 例程 | 序列 | 数据源与要点 |
|---|---|---|---|
| PostgreSQL | ✓ | ✓ | `pg_proc`（`prokind IN ('f','p')`，PG 10 以下回落 `proisagg`/`proiswindow`）;名字带 `pg_get_function_identity_arguments` —— **PG 允许重载**,只写 `proname` 就是几行一模一样的名字 |
| MySQL | ✓ | ✗ | `information_schema.ROUTINES`;MySQL 不允许重载，名字就是标识。**没有序列**：自增是列属性 |
| SQL Server | ✓ | ✓ | `sys.objects` 的 `P/PC/FN/IF/TF/AF`;`sys.sequences`（2012 起，老服务端 catch 掉返回空表） |
| Oracle | ✓ | ✓ | `ALL_OBJECTS` 而不是 `ALL_PROCEDURES` —— 后者把**包里的每个成员**也列成一行，一个 10 个方法的包就是 10 行同名节点。包（`PACKAGE`）归到"过程"一类 |
| SQLite | ✗ | ✗ | 两样都没有，用基类的空实现 |

**能力位为 false 时整个分类不画。** 给 MySQL 画一个恒空的"序列",
与"这个库真的没有序列"长得一模一样。

### 3.8 图标

走宿主主题字典里那套 lucide 图集（`Icon.*`，与 Redis 插件同一套），插件不自带资源。
挑选原则是**同级之间一眼分得开**,不是"像不像"：表用网格、视图用眼睛、
物化视图用叠层（"存下来的视图"）、过程用终端、函数用闪电、序列用有序列表。

用转换器而不是节点上的 `Geometry` 属性：取资源要碰 `Application.Current.Resources`，
那是界面层的东西;让节点碰它，节点就再也不能在没有 `Application` 的纯离线单测里构造 ——
而树的判定用例（双击、右键、系统分组）恰恰全是那一类。
取不到资源返回 `null`，`Path` 静默不画，树照常可用：**宿主换一版图集不该让插件的树打不开**。

### 4.1 顺手掀出来的一条既有脆弱用例

`PgBinaryFallbackTests.真机_pg_class_降级之后查得出来` 在本轮的全量跑里**间歇性变红**,
断言落在 `Assert.IsTrue(result.TextFallback)` 上。

**不是修复失效,是取样漂了。** 那条用例发的是 `select * from pg_class limit 20` ——
没有 `ORDER BY`,取的是**物理行序**的前 20 行。而服务端只在**真要输出某一格**时
才需要 `aclitem` 的二进制输出函数,所以走不走降级取决于"这 20 行里有没有非空 `relacl`"。
本轮新增的用例在同一个库(`ops_pg`)里反复建删表,把物理行序挪动了,
于是有时取到 20 行全 NULL。

真机数据:每个库里 `relacl` 非空的有 **206 行**(`information_schema` 那批视图自带 PUBLIC 授权),
而不带 `ORDER BY` 的前 20 行里当前只落进 **2 行** —— 余量本来就只有这么点。

两边都修了:

1. **新用例改用自己的库 `cross_pg`**,不再动 `ops_pg`。"各组用各组的库"本来就是这个仓库
   已有的惯例(`PostgreSqlOpsTests` 与 `PgBinaryFallbackTests` 的类注释里都写着"现建现用")。
2. **那条既有用例改成取样确定的**:用户原样的 `select * from pg_class limit 20`
   仍然用来证"查得出来、真有 20 行",降级那几条断言换成
   `order by (relacl is null), oid limit 20` —— 非空 `relacl` 排在前面,降级必然触发。
   末尾那条"NULL 仍然是 NULL"的断言相应改看 `relpartbound`(非分区表上恒为 NULL)。

只做第 1 条也能让它当下变绿,但那只是把地雷埋回去:**下一个在 `ops_pg` 里建表的人会再踩一次**。

改完连跑多遍全绿。

### 4.2 这一轮**自己**写出来又被用例抓回去的四处

记下来不是为了自罚,是因为这四处有一个共同点:**它们都不会以任何错误的形式出现**,
只会让界面安静地做一件不对的事。下一个动这块的人会遇到同一类陷阱。

| 写错了什么 | 表现 | 被谁抓住 |
|---|---|---|
| 缓存键拼的是 `桶\\0库\\0schema`,作废那侧按 `" 库 schema"` 后缀匹配 | **F5 没反应** —— 清不掉任何一条。而"库里真的没有那张新表"和这个长得一样 | `F5要真的重查而不是拿回缓存` |
| 作废范围只按 (库, schema) 精确匹配 | **在库节点上** F5 没反应,在 schema 上按才有。这个差别没有任何人能猜到 | `PostgreSQL_在库节点上F5要作废它底下每个schema的清单` |
| Oracle 那一支拿 `s.Name` 和自己比来判"当前" | 恒为真 → **30 个 schema 全部加粗**。全都加粗等于都没加粗,而截图上也看不出来(一屏里没有对照) | `Oracle_当前schema只能标一个` |
| 计数把"系统对象"分组算成一行 | 2 张用户表 + 1 张系统表 → `表 (3)`,**碰巧和真值相同**。一个蒙对的数字比一个明显错的更难发现 | 截图复看时数出来的 |

前两处是同一个根:**"生成键"与"匹配键"分写在两处**。改成记录类型之后这类错不可能再发生。

## 五、仍然欠着

按"用户会不会撞上"排序。

1. **触发器分类**。模型上有 `SqlObjectKind.Trigger`，`PostgreSqlPack.ListTriggersAsync`
   也已经写好（含 `NOT tgisinternal` 那条关键过滤），但 `IDialectPack` 的契约还没开这一格，
   另外四个方言也没写。Navicat 有这一栏。
2. **例程 / 序列的详情**。现在它们是树上的叶子，双击没有反应 ——
   看不到定义源码、参数、序列的当前值。这是"列得出来"与"用得上"之间的差距。
3. **树上的建/删对象**。右键只有「打开数据」「查看结构」两项，没有新建表/删表/重命名。
   表设计器只能改已有的表。
4. **Navicat 有而这里完全没有的**：数据传输/结构同步、ER 图、备份计划、查询构建器、
   用户与权限管理。这些不在本轮范围内，但要说清它们不存在。
5. **国产库与同族方言**（达梦 / 人大金仓 / TiDB / OceanBase / openGauss）一个都没测 ——
   与上一轮同一条欠账。
6. **一个库几千张表时的表现没有实测**。`_all` / `Children` 两份投影在过滤时是 O(n) 全量重建，
   本机数据集最大 9 张表，那条路等于没跑过。
7. **PG 10 及以下的例程回落路径未验证**（`proisagg`/`proiswindow`），
   SQL Server 2008 R2 以下的 `sys.sequences` 缺失回落同样未验证。手上只有新版服务端。
