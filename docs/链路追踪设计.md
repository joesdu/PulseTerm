# 链路追踪(Trace Route)设计

> 起草于 2026-07-25。目标:在 VelaShell 内建一个 mtr 级别的链路追踪面板,回答
> "从我这里到这台服务器,慢在哪一跳、丢在哪一跳"。本文只定义设计,尚未实现。

## 1. 为什么内建

用户已经会用 `mtr` / `tracert`,内建的价值不在于重复这些工具,而在于三件它们做不到的事:

1. **目标是现成的**。追踪对象就是当前聚焦的会话配置,不用手抄 IP;配了跳板机
   (`SessionProfile.JumpHostProfileId`)时能按段追踪,这是外部工具完全看不到的拓扑。
2. **两个方向都能测**。客户端侧(本机 → 服务器)排查"我这边的网",远端侧(服务器 → 任意目标)
   排查"服务器的出网"。运维现场十次里有八次要靠这两组数据对照才能定位问题在哪一段。
3. **结论可归档**。追踪结果可以直接导出、贴进工单,和会话记录、连接诊断在同一个界面体系里。

反过来说,不做的事同样明确:不做持续后台监控,不做告警,不做多目标批量拨测 —— 那是监控系统的活。

## 2. 关键前提:丢包率会骗人

这是整个功能里最容易做错、也最容易误导用户的一点,必须写在设计的最前面。

中间跳显示丢包,**绝大多数情况不是故障**。路由器对 "TTL 耗尽要回一个 ICMP Time Exceeded"
这件事是限速的(Linux 默认 `net.ipv4.icmp_ratelimit`,商用路由器同理),甚至直接不回。转发数据面
一切正常,只是控制面懒得理你。

判定规则(UI 与导出报告都必须按此口径呈现):

- **只有最后一跳(目标本身)的丢包才代表端到端丢包。**
- 某一跳丢包、其**后续跳不丢**,判定为 `ICMP 限速`,以灰色呈现,不计入告警。
- 丢包从某一跳开始**一直延续到最后一跳**,才判定为 `疑似真实丢包`,红色呈现。
- 整跳无响应(`* * *`)但后续跳有响应,判定为 `节点不响应`,不是断链。

延迟同理:某一跳 RTT 高而后续跳正常,是那台路由器的控制面慢,不是链路慢。**延迟只应沿链路单调
比较**,谁比前一跳明显高才是嫌疑人。

不把这三条做进判定逻辑,这个功能给出的就是一张会让人误判的表。

## 3. 数据模型

放在 `src/VelaShell.Core/Diagnostics/Trace/`。

```csharp
/// 一次探测的单个结果。
public sealed record TraceProbe(
    int Ttl,
    IPAddress? Address,     // null = 超时未响应
    TimeSpan? Rtt,          // null = 超时
    ProbeStatus Status);    // TimeExceeded / Reached / TimedOut / Unreachable / Error

/// 某一跳(TTL)的累计统计,对齐 mtr 的列。
public sealed class TraceHop
{
    public int Ttl { get; init; }

    /// 同一 TTL 观测到的全部地址。ECMP 多路径下一跳会返回多个 IP,
    /// 只留最后一个会让链路看起来在跳变。
    public IReadOnlyList<IPAddress> Addresses { get; }

    public string? HostName { get; }        // rDNS(PTR),未解析或失败为 null
    public string? AsnLabel { get; }        // "AS4134 CHINANET",默认不查,见 §8
    public int Sent { get; }
    public int Received { get; }
    public double LossPercent { get; }      // (Sent - Received) / Sent * 100
    public TimeSpan? Last { get; }
    public TimeSpan? Best { get; }
    public TimeSpan? Worst { get; }
    public TimeSpan? Average { get; }
    public double StdDevMs { get; }
    public double JitterMs { get; }         // 相邻两次 RTT 差的平均绝对值
    public IReadOnlyList<TimeSpan?> Recent { get; } // 最近 N 次,给迷你折线图用
    public HopVerdict Verdict { get; }      // §2 的判定结果
}

public enum HopVerdict { Ok, NoResponse, IcmpRateLimited, SuspectedLoss, Unreachable }

/// 一次追踪的完整结果。
public sealed class TraceResult
{
    public string Target { get; init; }         // 用户填的主机名
    public IPAddress? ResolvedAddress { get; init; }
    public TraceProtocol Protocol { get; init; }
    public TraceOrigin Origin { get; init; }    // Local / Remote
    public IReadOnlyList<TraceHop> Hops { get; }
    public bool TargetReached { get; }
    public int Rounds { get; }
    public DateTimeOffset StartedAt { get; init; }
}

public enum TraceProtocol { Icmp, TcpSyn, Udp }
public enum TraceOrigin { Local, Remote }
```

统计量采用**增量更新**(Welford 求方差),不保留全部历史样本 —— 追踪可以跑几十分钟,
每跳只留最近 N=60 次样本供画图。

## 4. 探测方式选型

### 4.1 客户端侧(P0)

用 `System.Net.NetworkInformation.Ping` + `PingOptions.Ttl`:发 TTL=1..n 的 ICMP Echo,
中间路由器回 `TimeExceeded`(`IPStatus.TtlExpired`),目标回 `EchoReply`(`IPStatus.Success`)。
这是最经典的 traceroute,且 `Ping` 在三大平台都可用,不必自己碰原始套接字。

```csharp
using var ping = new Ping();
PingReply reply = await ping.SendPingAsync(
    address, timeout, buffer, new PingOptions(ttl, dontFragment: true));
// reply.Status: TtlExpired → 中间跳,reply.Address 即该跳地址
//               Success    → 已到达目标
//               TimedOut   → 该跳无响应
```

权限现实(必须在文档和 UI 里如实说明,而不是让用户对着空表猜):

| 平台 | ICMP + TTL | 说明 |
|---|---|---|
| Windows | 免管理员 | 走 `IcmpSendEcho2`,普通用户即可 |
| Linux | 多数发行版可用 | .NET 优先用 `SOCK_DGRAM` ICMP,受 `net.ipv4.ping_group_range` 约束;不在允许组内则退化为调用系统 `ping`,**该路径拿不到 TTL 语义**,需检测并提示 |
| macOS | 免管理员 | `SOCK_DGRAM` ICMP 默认开放 |

Linux 上的退化路径是真实的坑:`Ping` 内部 fallback 到 `/bin/ping` 时,`PingOptions.Ttl` 不生效,
结果会变成"每一跳都直接命中目标"。启动时先做一次自检(TTL=1 打公网地址,看是否返回 TtlExpired),
自检失败就切到 §4.3 的外部命令模式,并在界面上说明原因,而不是给一张假表。

### 4.2 TCP SYN 追踪(P2)

ICMP 被沿途防火墙丢弃时,ICMP 追踪会在中途全变 `*`,但 SSH 明明连得上 —— 这种情况下必须
换成"向目标的 22 端口发 TTL 递增的 TCP SYN"。它更贴近真实业务流的路径(ECMP 哈希也按五元组走)。

代价是需要原始套接字构造 SYN 并收 ICMP 回包,Windows 上需要管理员,Linux 上需要 `CAP_NET_RAW`。
因此定为 P2,且只在 ICMP 模式全程超时时主动建议用户切换。

### 4.3 远端侧 / 外部命令模式(P1)

在会话现有的 SSH 连接上直接跑远端的工具,复用 `ISshClientWrapper.RunCommandAsync`
(与任务管理器同一条通道,无需新建连接):

1. 首选 `mtr --report --report-cycles N --json --no-dns <target>` —— JSON 输出,字段
   (`Loss%`/`Snt`/`Last`/`Avg`/`Best`/`Wrst`/`StDev`)可直接映射到 `TraceHop`,解析零歧义。
2. 退回 `traceroute -n -q 3 -w 1 -m 30 <target>`,文本正则解析。
3. 再退回 `tracepath -n <target>`(Debian 系默认自带,无需 root)。
4. 都没有:如实提示"远端未安装 mtr/traceroute/tracepath",并给出安装命令,**不猜、不伪造数据**。

探测命令用与任务管理器相同的分段标记约定(`echo __MTR__; ...`),先一次性探明远端有哪些工具,
避免每轮都试三遍。

同一套解析器也用于**本机外部命令模式**(§4.1 的 Linux 退化路径),差别只在执行器是本地进程还是
SSH 通道 —— 抽成 `ITraceCommandRunner` 一个接口两个实现即可。

## 5. 采集调度

- **轮次模型**:一轮 = 对 TTL 1..maxTtl 各发一个探针。轮内并发发送(每个 TTL 一个 `Ping` 实例),
  一轮的墙钟时间约等于单次超时,而不是 30 × 超时。
- **默认参数**:maxTtl=30,单探针超时 1s,轮间隔 1s,`Recent` 保留 60 个样本。
- **两种模式**:
  - *连续*(mtr 风格,默认):一直跑到用户停止,统计量持续收敛 —— 判断抖动和间歇丢包必须这样跑。
  - *单次*(traceroute 风格):每跳 3 个探针后结束,出一张静态表,适合贴工单。
- **收敛裁剪**:某个 TTL 连续 3 轮返回 `Success`(到达目标)后,停止探测更大的 TTL,并把该跳标为终点。
- **停止条件**:到达目标、达到 maxTtl、用户停止、会话关闭。
- 全程可取消(`CancellationToken`),窗口关闭即取消 —— 不留后台线程继续打网络。

## 6. 架构落位

沿用仓库既有分层,不新增模式:

| 层 | 类型 | 职责 |
|---|---|---|
| `VelaShell.Core/Diagnostics/Trace` | `ITraceRouteService`、`TraceHop`、`TraceOptions`、`TraceReportParser` | 契约 + 纯函数解析器(可单测) |
| `VelaShell.Infrastructure/Diagnostics` | `PingTraceRouteService` | 客户端 ICMP 实现 |
| 同上 | `CommandTraceRouteService` | 外部命令实现(本地进程 / SSH 通道两种 runner) |
| `VelaShell/ViewModels` | `TraceRouteViewModel`、`TraceHopViewModel` | 行复用、排序、增量统计、导出 |
| `VelaShell/Views` | `TraceRouteView.axaml` | 独立非模态窗口 |

服务以单例注册在 `InfrastructureServiceCollectionExtensions`,与 `IRemoteProcessService` 并列。

接口以流式回调返回,让界面边跑边刷新,而不是等全部跑完:

```csharp
public interface ITraceRouteService
{
    IAsyncEnumerable<TraceUpdate> RunAsync(TraceOptions options, CancellationToken ct = default);
}
```

## 7. 界面设计

**入口**:两处,同一条注册命令 `tools.trace`。

1. 标题栏功能区新增图标(`Icon.route` 已被隧道占用,新增 `Icon.milestone`),
   目标默认取当前聚焦会话;本地终端标签下仍可用(可手填目标),SFTP 标签下按当前会话的主机追踪。
2. 连接诊断中心(设计 RGXg1)追加一步"链路追踪",与既有四步检测并列 —— 诊断连不上时,
   这一步能直接看出是断在哪一跳。

**窗口布局**(独立非模态窗口,规格对齐任务管理器:自绘标题栏、可缩放、不透明背景):

```

```

细节:

- **行复用**:与任务管理器同样按 TTL 复用行对象,只更新字段。链路本身是稳定的,整表重建会让
  滚动位置和选中项每秒丢一次。
- **迷你折线**:最近 60 个样本的 RTT 走势,超时点画成断口。抖动问题一眼可见,比看 StDev 数字直观。
- **着色**:严格按 §2 的 `HopVerdict`,而不是简单地"丢包就标红"。
- **地址多值**:一跳有多个地址时主行显示首个,右侧标 `+2`,悬停展开 —— 这是 ECMP 的正常现象,
  要能看见但不该喧宾夺主。
- **右键**:复制该跳 IP / 复制整行 / 对该跳单独持续 ping / 查该 IP 的 ASN(需显式开启,见 §8)。
- **导出**:纯文本(mtr `--report` 同款排版,可直接贴工单)与 JSON 两种。

## 8. 隐私

rDNS 用系统 DNS 做 PTR 查询,属于常规网络行为,默认开启,可关。

**ASN / 地理归属默认关闭且不内置在线查询。**打开它意味着把沿途每一跳的 IP 发给第三方接口 ——
这些 IP 会暴露用户的网络路径与所在区域。要开必须由用户显式勾选,并在勾选处写明数据会发往哪个服务。
若后续要做,优先选可离线的数据库文件(用户自备),而不是默认联网。

不上报任何遥测。追踪结果只落在用户本机,导出与否由用户决定。

## 9. 分期

**P0 — 能用**
- `ITraceRouteService` + `PingTraceRouteService`(ICMP,连续/单次两模式)
- Linux TTL 自检与降级提示
- 独立窗口:表格 + 基础统计 + 开始/停止
- §2 的三条判定规则

**P1 — 好用**
- 远端追踪(mtr JSON / traceroute / tracepath 三级降级)
- rDNS 解析、迷你折线、文本与 JSON 导出
- 接入连接诊断中心作为第五步
- 跳板机链路分段追踪(按 `JumpHostProfileId` 逐段)

**P2 — 补齐边角**
- TCP SYN 追踪(ICMP 全程被过滤时)
- ASN/归属(显式开启,离线库优先)
- 同一跳多地址的展开视图

## 10. 测试策略

- **解析器**:`TraceReportParser` 是纯函数,用真实 `mtr --json` / `traceroute` / `tracepath`
  输出样本做表驱动测试 —— 含中间跳全 `*`、一跳多地址、主机名含括号等畸形输入。与
  `RemoteProcessProbeTests` 同样的写法。
- **统计量**:给定一串 RTT 序列断言 Loss/Avg/Best/Wrst/StDev/Jitter,以及 §2 的判定结果。
  这里必须专门测"中间跳丢包但末跳不丢 → IcmpRateLimited"这一条,它是最容易写反的分支。
- **调度器**:注入假的探针发送器,验证轮次推进、收敛裁剪、到达即停、取消即停,不打真实网络。
- **界面**:沿用既有 headless 测试,验证行复用与判定着色;不做需要真实网络的端到端测试。
