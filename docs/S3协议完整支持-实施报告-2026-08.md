## 一、范围修正（本次工作的起点）

第一版把「S3 支持」按 15 个操作（列举／上传／下载／删除／复制）来做，并据此判断
「自签 200 行 SigV4 比引 SDK 划算」。

本次先用反射统计了 `IAmazonS3` 的真实协议面：

| 类别 | 数量 |
|---|---|
| 对象读写与传输 | 约 20 |
| **桶级配置** | **约 55** |
| 对象级属性 | 约 20 |
| 其它（预签名、S3 Select、元数据表等） | 约 20 |
| **合计** | **116** |

**结论：先前那次 build-vs-buy 比较的分母是错的。** 覆盖 116 个操作意味着为每个操作重写一遍
XML 序列化与错误码映射，且 AWS 每加一个能力都要跟一次。第一版已推倒重做。

> **可复现**：统计方式是加载 `AWSSDK.S3` 后反射 `IAmazonS3` 的全部 `*Async` 方法去重计数，
> 而非依据记忆或文档目录。后续评估同类依赖时建议照做——先量协议面，再谈"两百行 vs 一个包"。

## 二、技术决策

**采用 AWSSDK.S3 4.0.102.1**（Apache-2.0，与本仓库 AGPL-3.0 + 商业双许可相容）。
手写的 SigV4 / REST 栈（`AwsSignatureV4`、`S3RestClient`、`S3Xml`）已删除。

代价是多两个程序集（AWSSDK.S3 + AWSSDK.Core，各约 1 MB）。收益是 116 个操作全部可达，
且分片上传的并发／重试／中止由 `TransferUtility` 承担。

**分层硬规则不变**：AWSSDK 的类型（`AmazonS3Exception`、`S3StorageClass` 等)
**不得越过 Infrastructure 边界**，翻译集中在 `S3Interop` 一处；Core 只见
`VelaShell.Core.S3` 下的中立契约与 `VelaS3*` 异常族。这与 FluentFTP、Tmds.Ssh 是同一条约定。

## 三、架构

两条服务线，共用同一条会话与同一个 `IAmazonS3` 客户端（经 `IS3ClientAccessor`）：

| 组件 | 契约 | 职责 |
|---|---|---|
| `S3FileService` | `ISftpService` + `IS3SessionService` | 文件管理器语义：平的键空间 → 目录树 |
| `S3ManagementService` | `IS3ManagementService` | 其余全部能力：桶配置、版本、ACL、对象锁定、标签、归档取回、分片上传管理、S3 Select |

因接缝仍在 `ISftpService`，**双栏浏览、传输队列、限速、拖放、冲突策略全部零改动**。

**桶配置收敛为一组三元方法** + `S3ConfigKind` 分派，而不是二十多组各自的方法
（那会让接口膨胀到七十多个成员）：

```csharp
Task<S3ConfigResult> GetBucketConfigAsync(session, bucket, S3ConfigKind kind, id?);
Task PutBucketConfigAsync(session, bucket, S3ConfigKind kind, string json, id?);
Task DeleteBucketConfigAsync(session, bucket, S3ConfigKind kind, id?);
Task<IReadOnlyList<string>> ListBucketConfigIdsAsync(session, bucket, S3ConfigKind kind);
```

新增一种配置 = **一个枚举成员 + 一个 switch 分支 + 一行导航项**。
这是"能覆盖完整"而非"覆盖一半"的结构性原因。

### 5.4 编辑器策略（一个刻意的取舍）

| 类型 | 适用 | 项目数 |
|---|---|---|
| 结构化表单 | 字段少、形状稳定 | 10（版本控制、公共访问阻止、对象所有权、加密、对象锁定、标签、静态网站、访问日志、传输加速、请求者付费） |

第二类硬做成表单不仅做不全，还会**在遇到未知字段时把用户已有配置改坏**——

即便是表单类，写回也走 JSON DOM 增量修改（`S3ConfigForm.Apply`），只覆盖表单确实编辑过的路径，
未知字段原样保留。该性质由 `S3ConfigFormTests.Apply_PreservesFieldsTheFormDoesNotKnowAbout` 钉死。

## 六、兼容性要点

真机上最容易翻车的三条，均已在 `S3ClientFactory` 中处理：

1. **`RequestChecksumCalculation` 调为 `WHEN_REQUIRED`** —— AWSSDK v4 默认对每个请求算 CRC32
   并要求响应回带校验和；较旧的 MinIO / Ceph RGW 与各类网关不认这些头，
   表现为上传直接被拒或下载报校验失败。
2. **`AllowAutoRedirect = false`** —— 区域重定向须由 SDK 按 `x-amz-bucket-region` 重签重发；
   自动跟随会带着**旧区域的签名**去请求新地址，必然 `SignatureDoesNotMatch`。
3. **`Auto` 寻址只在 `*.amazonaws.com` 用虚拟主机式**，其余一律路径式 ——
   自建 MinIO / Ceph 默认不解析 `bucket.host`（要配 `MINIO_DOMAIN`），而路径式两边都能工作。

其余：

- **「没配过」与「不支持」识别为空状态而非错误**（`S3Interop.IsMissingOrUnsupported`）。
  AWS 对每种未配置能力有专属错误码，兼容实现则常直接回 501；当成错误会让桶管理器一打开就一片红。
- **自签证书**复用 FTPS 那套「先拒绝 → 提示 → 记指纹后重连」流程与同一组 `Cert_*` 文案。
- **分片数上限 10000**：分片大小按 `max(配置值, 文件大小/10000)` 上调。
- **内容类型只在发起分片上传那一步能定**（`UploadPart` / `Complete` 都没有机会再给）。

### 7.1 环回服务器为什么仍校验签名

产品侧签名已由 SDK 负责，但 `LoopbackS3Server` 按收到的**原始请求行**重算 SigV4 并比对，
守的是另一半：**客户端配置（端点／区域／寻址方式／凭据）有没有被正确送上线**。
这类错误在真实服务端只回一句 `SignatureDoesNotMatch`，毫无线索。

校验器自己就是判据，因此它自己也必须被验证——这正是 `SigV4VerifierTests` 保留的意义。

### 7.2 写测试过程中查出并修复的真实缺陷

| 缺陷 | 影响 |
|---|---|
| 分片上传丢失对象内容类型 | 大于阈值的 `.html` / `.png` 全部退化为 `application/octet-stream`，分享出去会变成下载文件 |
| 表单保存时空白标签键未被丢弃 | 全空格的键会被服务端拒绝，用户看到一次无谓的失败 |
| 删除桶会代为清空 | **最严重**：根视图下桶与普通目录外观一致，确认框只说「删除文件夹 xxx?」，一次误点会连带删掉整桶数据。已改为如实透出 `BucketNotEmpty`——S3 拒绝删非空桶本身就是安全属性，客户端不应绕过 |
