# Xshell 兼容登录（外部拉起）

> 面向：把 VelaShell 接进堡垒机 / SSO / 运维门户的用户与管理员
> 相关代码：`src/VelaShell.Infrastructure/Startup/`、`src/VelaShell/Services/ExternalLaunchCoordinator.cs`、`src/VelaShell/Services/UrlProtocolRegistration.cs`

## 1. 它解决什么问题

企业里的服务器登录往往不经过终端软件自己的连接管理：用户在堡垒机 / SSO 门户的网页上点一下「用终端打开」，
网页把一段临时凭据交给本机的安全客户端，客户端再拉起终端软件登录目标主机。**用户自己并不知道密码**——
密码是堡垒机现发的一次性口令，用完即废。

问题在于，这些第三方客户端只认 Xshell（以及 SecureCRT、PuTTY）的调用约定。要让 VelaShell 出现在那颗按钮后面，
它必须能被**按 Xshell 的方式**拉起。本功能就是这条兼容层。

## 2. 支持的调用形态

| 形态 | 例子 | 说明 |
|---|---|---|
| `-url` | `VelaShell.exe -url ssh://root:one-time@10.0.3.21:2222` | 最常见；堡垒机客户端的默认写法 |
| `-newtab` | `VelaShell.exe -newtab ssh://root@10.0.3.21` | 与 `-url` 等价（应用本就以标签页打开） |
| 裸 URL | `VelaShell.exe ssh://root@10.0.3.21` | 部分调用方把 URL 直接放在第一个参数上 |
| 会话文件 | `VelaShell.exe -f C:\Temp\session.xsh` | 读 UTF-16 的 `.xsh`，取主机 / 端口 / 用户名 / 协议 |
| 显式选项 | `-l <user>` `-p <port>` `-pw <password>` `-i <keyfile>` | 覆盖 URL 中的同名字段，优先级与 Xshell 一致 |

支持的 scheme：`ssh`、`sftp`、`ftp`、`ftps`。`telnet` / `rlogin` 会被识别但给出「不支持的协议」提示——
**刻意不静默丢弃**，否则用户在网页上点了半天完全没有反应。

**刻意不实现的**：Xshell 的 `-e` / `-s`（连上后自动执行命令 / 脚本）。让外部调用方顺带指定「连上去跑什么」，
等于把远程命令执行挂在一条 URL 上——这是本兼容层里唯一真正会放大危害的能力，收益（省一次粘贴）远不抵风险。

URL 解析刻意手写而非交给 `System.Uri`：一次性口令里出现未转义的 `@ : / #` 是常态，`Uri` 遇到会判非法或把主机截错。
解析规则是「authority 里最后一个 `@` 才是主机分界，用户名与密码在第一个 `:` 处切开」，`%XX` 转义照常解码。

## 3. 系统协议关联（ssh:// / sftp://）

设置 → 安全与审计 → 外部登录 → **关联 ssh:// 与 sftp:// 链接**（默认关闭）。

- Windows：只写 `HKCU\Software\Classes\{ssh,sftp}`，当前用户生效，不需要管理员。命令行形如 `"…\VelaShell.exe" -url "%1"`。
- Linux：写 `~/.local/share/applications/velashell-url-handler.desktop` 并调 `xdg-mime`。
- macOS：scheme 只能由 app bundle 的 `Info.plist` 声明（打包期决定），运行时改不了，开关静默跳过。

关闭开关时**只删本应用写的键**（按注册表里的 `VelaShellManaged` 标记识别）——不会连带清掉 Xshell、MobaXterm 等其他软件的关联。

## 4. 单实例转发

应用已经开着时，网页那一次点击起的是**第二个进程**。它不再弹「已在运行」就退出，而是：

1. 抢单实例互斥体失败 → 说明已有实例；
2. 经命名管道把请求（含一次性凭据）交给运行中的实例，等一个字节的回执；
3. 收到回执才静默退出；转发确实失败时才退回「已在运行」提示框。

管道两端都带 `PipeOptions.CurrentUserOnly`：Windows 上 ACL 收成仅当前用户，Unix 上 socket 权限 0700，
且客户端会核对服务端属主——同机的**另一个用户**既连不上，也伪造不出一个假服务端来钓走口令。

不带任何参数的第二次启动（双击图标、托盘里已隐藏）会转成一次「唤到前台」。

## 5. 凭据处理

一次性凭据的红线是**不落盘**，具体保证：

- 由请求建出的会话配置 `RememberPassword = false`，且**从不写入会话仓储**（不会出现在会话树里）；
- 「最近连接」历史只记 主机 / 端口 / 用户名 / 耗时，本就不存密码；
- `ExternalLaunchRequest.ToString()` 刻意不含密码——这条串随时可能被 `Trace` 抄进日志文件；
- 请求不带凭据时，优先复用**已保存的同目标配置**（用你自己存的密码 / 密钥），行为等同于点侧边栏那一条。

## 6. 安全分析

这条路径与在界面里点「连接」有一处本质区别：**目标和凭据都是别人给的**。以下逐条列出风险与对策。

| 风险 | 是否可根除 | 现状 |
|---|---|---|
| **任何本机进程都能让终端连上任意主机**（包括浏览器里的一个 `ssh://` 链接） | 否——同用户进程等价于用户自己 | 默认开启的**确认弹窗**：显示目标、来源、是否随请求带了凭据，用户点「连接」才建会话；可按 `scheme://user@host:port` 逐个信任 |
| **密码出现在命令行里**，同用户的其他进程（以及 EDR / Sysmon 的进程创建日志）能读到 | 否 | 这是 Xshell / SecureCRT / PuTTY 同款风险，属于该调用约定本身。缓解只能在源头：让堡垒机下发**一次性口令**而非长期密码，并尽量用 `-f` 会话文件或代理端口方案代替 `-pw` |
| 恶意网页伪造 `ssh://` 链接指向攻击者主机（骗你把凭据/操作送过去） | 是 | 确认弹窗把目标原样摆出来；协议关联默认关闭，不开就没有这条入口 |
| 同机另一用户嗅探或劫持转发通道 | 是 | 命名管道 `CurrentUserOnly`（Windows ACL / Unix 0700 + 属主核对） |
| 一次性口令被写进配置、日志、同步数据 | 是 | 见上一节的四条保证 |
| 拉起请求绕过主机指纹校验 | 是 | 不绕——外部拉起复用同一条连接流水线，首次指纹确认 / 指纹变更阻断照常生效 |

**给管理员的建议**

1. 堡垒机侧下发一次性口令，并把有效期压到秒级；不要用 `-pw` 传长期密码。
2. 保持「连接前先确认」开启。关掉它意味着任何本机进程都能让终端静默连上服务器——
   在共享终端、演示机、或用户会随手点开网页链接的环境里，这是实打实的攻击面。
3. 只在确有需要时开启协议关联；不需要网页直接唤起的话，让堡垒机直接指向 `VelaShell.exe` 路径即可，零系统侵入。
4. 「已信任的外部目标」是可清空的：设置 → 安全与审计 → 外部登录 → 清空。

**一句话结论**：兼容 Xshell 这套登录方式本身不会让 VelaShell 比 Xshell 更不安全，因为风险来自调用约定
（密码走命令行、任何本机进程都能发起），不来自实现。真正能拉开差距的是默认要不要确认——本应用默认要。

## 7. 设置项对照

| 设置（安全与审计 → 外部登录） | 默认 | 作用 |
|---|---|---|
| 接受外部登录请求 | 开 | 关掉后 `-url`、`-f` 与协议关联一律忽略 |
| 连接前先确认 | 开 | 弹窗显示目标与来源，确认才连 |
| 关联 ssh:// 与 sftp:// 链接 | 关 | 写 / 删当前用户的协议关联 |
| 已信任的外部目标 | 空 | 勾过「不再询问」的目标，可一键清空 |

## 8. 堡垒机接入示例

```
# 直接指定可执行文件（推荐，零系统侵入）
"C:\Program Files\VelaShell\VelaShell.exe" -url ssh://%USER%:%ONETIME%@%HOST%:%PORT%

# 走系统协议关联（需先在设置里开启）
ssh://%USER%:%ONETIME%@%HOST%:%PORT%

# 落一个临时会话文件（凭据不进命令行，登录时由用户或密钥完成认证）
"C:\Program Files\VelaShell\VelaShell.exe" -f "C:\Temp\jump-1234.xsh"
```
