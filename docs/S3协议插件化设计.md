## 〇、这一版做了什么

S3 支持**从宿主内建改成了插件**（`plugins/VelaShell.Plugin.S3`）。协议实现、AWSSDK 依赖、
桶管理器与对象检视器界面、149 条 S3 文案全部移出宿主；宿主侧新增一个通用的
**协议能力域**（插件 SDK 的 `IProtocolFileSystem` + 宿主的注册表与适配器），
S3 只是它的第一个使用者。

换来的三件事：

1. **不用 S3 的用户不再为它付费**：AWSSDK.S3 + AWSSDK.Core（各约 1 MB）不进宿主进程，
   插件目录按需分发；不打开 S3 页签就一行代码都不会被装载。
2. **宿主不再认识任何具体协议**：`ConnectionType` 里没有 `S3` 了，只有一个 `Plugin`；
   再接入 WebDAV / GCS / 阿里云 OSS 原生 SDK，宿主一行都不用改。
3. **第三方可以自己接协议**：能力域是公开 SDK 的一部分，不是 S3 的私有后门。

代价与边界写在 §十。

## 一、结论先行

**S3 不是"上传下载"那么小的协议。** 按 `IAmazonS3` 反射统计，它有 **116 个操作**：

| 类别 | 数量 | 例子 |
|---|---|---|
| 对象读写与传输 | 约 20 | Get/Put/Copy/Delete/Multipart 全家 |
| 桶级配置 | 约 55 | 版本控制、生命周期、策略、ACL、CORS、加密、对象锁定、复制、通知、清单… |
| 对象级属性 | 约 20 | 标签、ACL、保留、合法保留、归档取回、属性 |
| 其它 | 约 20 | 预签名、S3 Select、目录桶、元数据表 |

**因此本特性分两条线，两条线共用同一条会话与同一个客户端：**

| 组件 | 契约 | 职责 |
|---|---|---|
| `S3ProtocolFileSystem` | SDK 的 `IProtocolFileSystem` | 文件管理器语义：把平的键空间翻译成目录树 |
| `S3ManagementService` | 插件自有的 `IS3ManagementService` | 其余全部：桶配置、版本、ACL、对象锁定、标签、取回、分片上传管理、S3 Select |

界面同样两条线：宿主既有的双栏文件浏览器（零改动复用），加上 **S3 桶管理器**与
**S3 对象检视器**两个插件面板。

## 二、为什么用 AWSSDK.S3 而不是自己实现

**这一条在 2026-08-14 被推翻重做过，值得记录原委。**

第一版选择了自己实现 SigV4 + REST。那个判断建立在一个**错误的范围假设**上——以为"S3 支持"约等于
列举、上传、下载、删除、复制这十来个操作。在那个假设下，自签 200 行确实比拖进一整套 SDK 划算。

范围一旦按协议实际大小重新界定（116 个操作），账立刻反过来：

| 维度 | 自己实现 | AWSSDK.S3 |
|---|---|---|
| 覆盖 116 个操作的代码量 | 每个操作各写一遍 XML 序列化 + 错误码映射，数千行 | 已有 |
| 新增/变更的 AWS 能力 | 每次都要重做一遍 | 升包 |
| 分片上传的并发/重试/中止 | 自己写 | `TransferUtility` |
| 许可 | — | Apache-2.0，与本仓库 AGPL-3.0 + 商业双许可相容 |
| 代价 | — | 多两个程序集（AWSSDK.S3 + AWSSDK.Core，各约 1 MB） |

**教训**：依赖取舍必须先量清楚协议面，再谈"两百行 vs 一个包"。先前那次比较的分母是错的。

> 与 FTP 侧选 FluentFTP 用的是同一把尺子：协议面大、状态机复杂、自己写风险高时选成熟库。
> 两处结论一致，只是第一版对 S3 的协议面估错了。

**分层约束不变，只是边界挪了位置**：AWSSDK 的类型（`AmazonS3Exception`、`S3StorageClass` 等）
**不得越过插件程序集边界**——与宿主里 FluentFTP / Tmds.Ssh 同一条硬规则。
插件内部认 `VelaS3*` 异常族（翻译在 `S3Interop` 一处完成），出口再翻成 SDK 的
`Protocol*` 四类（认证 / 证书 / 连接 / 不支持），宿主侧再翻成 `VelaShell.Core.Protocols`
的中立异常族。

两段翻译看着多余，实则各有分工：`VelaS3*` 要区分「没配过 / 不支持 / 权限不足 / 不存在」
——桶管理器的空状态全靠它；而宿主只关心那四类，多出来的区分对它没有意义。

## 三、核心设计一：平的键空间 → 目录树

S3 的键空间是平的，`/` 只是键名里的一个普通字符。约定的映射（`Core/S3/S3ObjectPath.cs`）：

| 路径 | 含义 |
|---|---|
| `/` | 根 = 桶列表（每个桶显示为一个目录） |
| `/bucket` | 桶根 = 以 `""` 为前缀、`/` 为分隔符列举 |
| `/bucket/a/b` | 键 `a/b`，或前缀 `a/b/`（取决于它是对象还是"目录"） |

四条规则：

1. **「子目录」来自 `CommonPrefixes`**（带 `delimiter=/` 列举时由服务端折叠）。
2. **空目录是一个以 `/` 结尾的零字节对象**。这是 S3 生态的既成约定；建目录时造它，列举时隐掉它。
3. **重命名/移动没有原语**，一律"服务端复制 + 删除"。顺序不能反：复制成功后才删源。
4. **chmod 没有对应语义**，明确抛 `VelaS3UnsupportedOperationException`；访问控制走 ACL 与桶策略。

### 3.1 与 SFTP/FTP 语义不同的地方

| 能力 | SFTP / FTP | S3 | 处理 |
|---|---|---|---|
| 上传续传 | 服务端有半个文件可续 | **写入是原子的**，失败不留残留 | `resumeOffset` 被忽略，整份重传（如实写在方法文档里） |
| 下载续传 | 支持 | 支持（`Range`） | 正常实现；服务端不认 `Range` 时回落从头写 |
| 同站复制 | FTP 无 | **服务端复制** | S3 在这一项上优于 FTP |
| 目录修改时间 | 有 | 无（目录是虚构的） | 给 `DateTime.MinValue` 让界面留空 |
| 属主 / 属组 | 有 | 只有属主 | 属组留空，**不拿存储类别去填**——填进去只会让列名说谎 |

### 3.2 桶只删空的，绝不代为清空

`DeleteBucket` 要求桶为空，这是它的**安全属性**：桶是顶层的、常被多方共享的资源，名字一旦释放可能被别人抢占。
而在文件浏览器里，根视图下的桶与普通目录长得一样，删除确认也只说一句「删除文件夹 xxx?」。
若客户端代为清空再删桶，一次误点就会连带删掉整桶数据。因此如实透出 `BucketNotEmpty`。

> 递归删**前缀**照常支持——那与 SFTP/FTP 的"删文件夹"语义一致，用户预期相同。

## 四、核心设计二：桶配置收敛成一组三元方法

S3 的二十多种桶配置在协议上是同一个形状：`GetBucketXxx` / `PutBucketXxx` /（部分有）`DeleteBucketXxx`，
差别只在载荷。因此 `IS3ManagementService` 不为每种配置各开三个方法（那会让接口膨胀到七十多个成员），
而是收敛成：

```csharp
Task<S3ConfigResult> GetBucketConfigAsync(session, bucket, S3ConfigKind kind, id?);
Task PutBucketConfigAsync(session, bucket, S3ConfigKind kind, string json, id?);
Task DeleteBucketConfigAsync(session, bucket, S3ConfigKind kind, id?);
Task<IReadOnlyList<string>> ListBucketConfigIdsAsync(session, bucket, S3ConfigKind kind);
```

**新增一种配置 = 一个枚举成员 + 一个 switch 分支 + 一行导航项**，三处都是几行。
这正是这套功能能"完整覆盖"而不是"覆盖一半"的原因。

### 4.1 载荷为什么用 JSON

若为每种配置在 Core 里造 DTO 再手写双向映射，代价是上千行搬运代码，且——**更糟的是**——
漏掉的字段会在写回时被静默清空（读进来渲染不出的字段，序列化回去就没了）。那会真的改坏用户的生产配置。

直接序列化 SDK 的模型对象则天然完整：读到什么就是什么。结构化表单只是这份 JSON 的一个**视图**，
写回时走 JSON DOM 增量修改（`S3ConfigForm.Apply`），只覆盖表单确实编辑过的路径，
其余原样保留。这条性质由 `S3ConfigFormTests.Apply_PreservesFieldsTheFormDoesNotKnowAbout` 守住。

### 4.2 表单 vs JSON 编辑器

| 编辑器 | 适用 | 配置项 |
|---|---|---|
| 结构化表单 | 字段少、形状稳定 | 版本控制、公共访问阻止、对象所有权、加密、对象锁定、标签、静态网站、访问日志、传输加速、请求者付费 |
| JSON 文档编辑器 | **本身就是文档** | 生命周期、桶策略、ACL、CORS、复制、事件通知、清单、分析、指标、智能分层、元数据表、ABAC |

第二类硬做成表单既做不全，也会在遇到未知字段时改坏配置——AWS 控制台在这些项上同样给 JSON。
**给文档编辑器不是偷懒，而是更完整、更安全的选择。**

## 五、界面

### 5.1 连接配置页（宿主渲染，插件只声明）

S3 页签**不是**写在 `ConnectionProfileView.axaml` 里的，而是插件在 `plugin.json` 的
`contributes.protocols` 里声明的一条数据。连接表单（区域 / 寻址方式 / HTTPS / 默认桶 /
会话令牌 / 分片大小 / 并发数 / 存储类别 / 加密 / 目录占位符)同样是数据——插件在
`ProtocolDescriptor.Fields` 里声明字段的键、标签、形态与默认值，宿主按形态渲染控件。

**插件因此没有一行连接对话框的界面代码。** 这与蓝图 08 明确不做的通用声明式 UI 是两回事：
那是任意界面，这只是一张形状封闭的参数表（文本 / 口令 / 布尔 / 整数 / 下拉，五种），
语义确定、可校验、可主题化。连接对话框是宿主的核心界面，布局与交互该由它统一负责。

### 5.2 文件浏览器（既有，零改动复用 + 三个声明式菜单项）

宿主的远程文件契约是协议无关的，因此双栏浏览、传输、限速、拖放、冲突策略全部零改动。
右键菜单里多出的三项来自 `ProtocolDescriptor.Actions`：

- **复制分享链接** — 预签名 URL（7 天）
- **S3 对象管理…** — 打开对象检视器
- **桶管理…** — 打开桶管理器

动作是**声明式**的（随协议描述一起给出），因此菜单在按下右键那一帧就能画出来；
换成「每次右键回调插件问一遍」会多一次异步往返，菜单明显慢半拍。
点击后宿主只把「哪个动作 + 哪个路径」转交给插件，做什么完全由插件决定。

### 5.3 S3 桶管理器 / 对象检视器（插件面板）

两扇界面现在是插件用完整 Avalonia 自绘的面板，经 `context.Ui.ShowPanelAsync`
以 `PanelDisplayMode.Window` 打开——窗口外壳（标题栏、圆角、明暗主题）由宿主提供，
插件只画内容并一律使用 `{DynamicResource VelaXxx}` 主题令牌，因此看上去仍是宿主的一部分。

导航由 `S3ConfigDescriptor.All` 驱动，**协议里有的这里就有**。

| 页面 | 覆盖的操作 |
|---|---|
| 概览 | `GetBucketLocation`、`GetBucketPolicyStatus`、`GetBucketVersioning`、`GetObjectLockConfiguration` |
| 对象版本 | `ListVersions` + 删除指定版本 + 恢复历史版本（以复制实现） |
| 未完成分片上传 | `ListMultipartUploads` + `AbortMultipartUpload` |
| 22 项配置 | 见 §四的 `S3ConfigKind` |

对象检视器分页签：详情 / 标签 / 权限 / 保留与合法保留 / 存储与加密 / S3 Select，覆盖
`GetObjectAttributes`、`GetObjectMetadata`、`Get/Put/DeleteObjectTagging`、`Get/PutObjectAcl`、
`Get/PutObjectRetention`、`Get/PutObjectLegalHold`、`RestoreObject`、`CopyObject`（改存储类别/加密/元数据）、
`SelectObjectContent`、`GetPreSignedURL`。

> 面板视图模型**不引 ReactiveUI**：插件 ALC 里那份 `RxApp` 与宿主的是两个独立实例，
> 它的 `MainThreadScheduler` 不会自动挂到 Avalonia 调度器上，命令的 `CanExecuteChanged`
> 会在后台线程触发绑定更新。插件自带八十行的 `ObservableObject` + `AsyncCommand` 更稳，
> 也省掉三个随插件分发的程序集。

## 六、兼容性要点（容易踩的坑）

1. **`RequestChecksumCalculation` 必须调成 `WHEN_REQUIRED`。** AWSSDK v4 默认对每个请求算 CRC32
   并要求响应回带校验和；相当一部分 S3 兼容实现（较旧的 MinIO / Ceph RGW / 各类网关）不认这些头，
   表现为上传被拒或下载报校验失败。
2. **`AllowAutoRedirect` 必须为 false。** 区域重定向要由 SDK 按 `x-amz-bucket-region` 重签重发；
   自动跟随会带着旧区域的签名去请求新地址，必然 `SignatureDoesNotMatch`。
3. **寻址方式的默认值要保守**：`Auto` 只在 AWS 自家端点（`*.amazonaws.com`）用虚拟主机式，其余一律路径式。
   自建 MinIO / Ceph 默认不解析 `bucket.host`（要配 `MINIO_DOMAIN`），而路径式两边都能工作。
4. **"没配过"与"不支持"不是错误**，是空状态。AWS 对每种未配置的能力有专属错误码
   （`NoSuchLifecycleConfiguration`、`NoSuchCORSConfiguration`…），兼容实现则常直接回 501。
   当成错误会让桶管理器一打开就一片红——`S3Interop.IsMissingOrUnsupported` 专门识别这一类。
5. **自签证书**走与 FTPS 完全相同的「先拒绝 → 提示 → 记指纹后重连」流程，两协议共用同一个对话框
   与同一组 `Cert_*` 文案。刻意不在 TLS 回调里同步等用户点按钮（那要把异步对话框阻塞成同步，极易死锁）。
6. **分片数上限 10000**：分片大小按 `max(配置值, 文件大小/10000)` 上调，否则 100GB 的文件会在第 10001 片被拒。
7. **内容类型只在发起分片上传那一步能定**（`UploadPart`/`Complete` 都没有机会再给）。

## 七、凭据与安全

- **Access Key ID → `SessionProfile.Username`，Secret Access Key → `SessionProfile.Password`。**
  复用通用字段而不是另开两个：「记住密码」的 AES 加密落盘、登录弹窗、导入器的凭据还原全部零改动。
- **STS 会话令牌**是 `S3Settings.SessionToken`，同样是凭据，落盘前单独加密。
- **匿名访问是一条正当路径**（公开只读桶）：两者都空时不弹登录框，直接按匿名连；
  只有「填了 Access Key 却没有 Secret」才算真的缺凭据。
- **明文 HTTP** 在连接弹窗里给出警告：密钥仍受签名保护，但对象内容是裸的。

### 8.1 环回服务器为什么仍校验签名

`LoopbackS3Server` 会按收到的**原始请求行**重算 SigV4 并比对。产品侧的签名虽已由 SDK 负责，
但这条校验守的是另一半：**客户端配置（端点／区域／寻址方式／凭据）有没有被正确送上线**。
这些配错时，真实服务端只回一句 `SignatureDoesNotMatch`，毫无线索。

校验器自己就是判据，所以它自己也必须被验证——`SigV4VerifierTests` 拿 AWS 官方文档的 5 组示例
对它逐段对拍（规范请求 / 待签串 / 签名），否则一个错误的校验器会把什么都放行。

> **仍待真机验证**：以上结论都在环回服务器上成立。上线前建议拿 MinIO（自签证书 + 路径式）
> 与真实 AWS S3（虚拟主机式 + 跨区域桶 + 版本控制 + 对象锁定）各跑一次，
> 重点是 §六 的 1／2／3 条在真实实现上的行为。

## 九、未覆盖的操作（明确的边界）

116 个操作里有 4 个**客户端无法或不应调用**，其余全部可达：

| 操作 | 为什么不做 |
|---|---|
| `WriteGetObjectResponse` | 只能从 S3 Object Lambda 函数内部调用，桌面客户端物理上无法使用 |
| `CreateSession` | S3 Express 目录桶的内部会话令牌，由 SDK 自动管理 |
| `GetObjectTorrent` | BitTorrent 分发，AWS 已弃用 |
| `ListDirectoryBuckets` | S3 Express One Zone 专属；本特性面向通用 S3 与兼容实现，等有需求再开 |

`InitiateMultipartUpload` / `UploadPart` / `CompleteMultipartUpload` / `CopyPart` 不在界面上直接暴露——
它们由传输引擎在内部使用；分片上传的**管理**（列出、中止）在桶管理器里。

## 十、插件化的代价与边界

**代价一:协议能力仅 `inProcess`。** 协议是宿主**反向调用插件**的高频通道
(列目录、流式读、传输进度),而隔离进程的 RPC 目前只承载插件→宿主的请求方向。
声明了 `contributes.protocols` 却又要 `hostMode: "isolated"` 的清单在发现期就被拒绝并给出原因
——比让它装上去、表现成「页签在、点了连不上」要好得多。代价是 S3 插件崩溃会影响宿主进程;
考虑到它是第一方插件、且与宿主同源构建,这个取舍可以接受。放开它需要把 RPC 做成双向请求,
属于蓝图 05 的后续工作。

**代价二:限速要由宿主喂给插件。** 全局带宽上限是**用户偏好**,对 SFTP/FTP/插件协议一视同仁,
不能让每个协议插件各配一份(用户得配三遍,而且「总带宽上限」从此说不清)。因此 SDK 增加了
`IProtocolsApi.GetTransferOptionsAsync()`,插件在每次传输开始时现问一次;
`ThrottledStream` 则在插件里复制了一份(153 行、零依赖的令牌桶)。

**代价三:文案要各带一份。** 149 条 S3 文案从宿主的五个 `.resx` 移进了插件自带的
`Loc.cs`,只保留中英两套 —— 宿主支持五种语言,但让宿主替一个它并不认识的协议背词典
是本末倒置;缺哪种语言就回落英文,而不是显示一个键名。

**明确不做:老数据迁移。** `ConnectionType` 的 3 号值(曾短暂用于内建 S3)已退役且**不复用**,
读到它一律降级为 SSH。内建 S3 从未进入任何已发布版本,没有需要迁移的用户数据;
为不存在的数据留一条永久的迁移分支,只会在将来误伤真正的插件配置。

**边界:协议 id 发布后不可更改。** 它落在用户的会话配置里(`SessionProfile.PluginProtocolId`),
改名等于让所有老配置认不出自己的协议。id 另被强制全小写 —— 它要在注册表、界面、落盘配置
三处被比较,允许大写就会出现"同一个 id 在不同环节被判成不是同一个"。
