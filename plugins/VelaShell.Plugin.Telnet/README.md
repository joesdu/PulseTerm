# VelaShell Telnet 插件

RFC 854 Telnet 终端。以 SDK 的**终端协议能力**(`IProtocolTerminal`)接入宿主:
连接页多出一个 Telnet 页签,用它建的会话打开的是普通终端标签 ——
VT 引擎、回滚、搜索、会话日志、会话录制、ZMODEM 全部是宿主的既有实现,插件只负责
"把字节搬过去"和 RFC 854 的选项协商。

| | |
| --- | --- |
| id | `velashell.telnet` |
| 默认端口 | 23 |
| 装载模式 | 进程内(协议能力的硬性要求) |
| 激活时机 | `onProtocol:velashell.telnet` —— 用户点到 Telnet 页签才装载 |
| 依赖 | 无(只用 `TcpClient` + SDK) |

## 为什么自己实现协议

截至 2026-08,没有可直接用作 VT100 全屏终端网络层的成熟 .NET Telnet 库:
`PrimS.Telnet` 不做真协商(定位是"发命令抓响应"),`TelnetNegotiationCore` 做协商但
面向 MUD 且自述不提供 VT 仿真,`TentacleSoftware.Telnet` 已废弃。
而 RFC 854 的协议面很小,本仓库又**已经有完整的 VT 引擎**,缺的只是协商层 ——
为几百行代码引一个 MUD 导向的依赖不划算。取证见
[docs/Telnet与串口可行性调研.md](../../docs/Telnet与串口可行性调研.md) §4.2。

## 协商集

| 选项 | 码 | 方向 | 作用 |
| --- | --- | --- | --- |
| ECHO | 1 | 对端 | 与 SGA 同时生效才是逐字符远端回显(RFC 858),vim/htop 能跑的前提 |
| SUPPRESS-GO-AHEAD | 3 | 双向 | 同上 |
| TERMINAL-TYPE | 24 | 我方 | 上报 TERM,否则对端不知道该发什么转义序列 |
| NAWS | 31 | 我方 | 上报窗口行列,否则 htop/vim 按 80x24 画 |
| BINARY | 0 | 双向 | 8 位透明:UTF-8 与 ZMODEM 完整传输的前提 |

三处最容易漏、且漏了极难定位的地方(都有专门的单测钉着):

1. **IAC 双写覆盖所有字节路径** —— 数据里字面的 `0xFF` 发成 `IAC IAC`,收到还原。
   漏了的表现是"平时都好,输出含 0xFF 时随机损坏",ZMODEM 首当其冲。
2. **子协商载荷里的 0xFF 同样要双写** —— NAWS 只在窗口宽或高**恰为 255** 时才触发。
3. **CR 改写的作用域** —— 谈成 BINARY 后一律不改写。改写只对"用户按的回车"成立,
   而传输层看到的还有粘贴内容与 ZMODEM 帧,对整条出方向流改写会把它们打坏。

## 连接表单

| 字段 | 默认 | 说明 |
| --- | --- | --- |
| 终端类型(TERM) | 跟随宿主设置 | 老设备可能只认 `vt100` |
| 回车键发送 | CR LF | RFC 1123 §3.3.1 建议;可选 CR NUL / 裸 CR。BINARY 生效后此项不参与 |
| 请求 8 位(BINARY) | 开 | 高级选项 |
| 本地回显 | 自动 | 高级选项。自动 = 对端未接管 ECHO 时本地回显,不会出现"打字看不见" |

用户名/口令两栏由 `ProtocolFeatures.NoCredentials` 收起:Telnet 的登录发生在带内
(对端打印 `login:`,用户直接在终端里敲),摆两个填了也发不出去的框只会误导。

## 安全提醒

**Telnet 是明文协议**:没有主机身份校验、没有加密,凭据在网络上裸奔。
宿主的 known-hosts / 主机信任那条链路对它完全不适用。仅在受控网络里对着
不支持 SSH 的老设备使用。状态栏会显示 `Telnet • <名称>` 而不是 `SSH • …`,
就是为了不让人误以为与 SSH 同等安全。

## 测试

`tests/VelaShell.Plugin.Telnet.Tests` 分两层:

- **协商状态机**:期望值按 RFC 原文的字节序列手写,不是"跑一遍看输出写什么"。
- **会话**:跑在真实的环回 `TcpListener` 上 —— 协商时序、IAC 边界、本地回显、
  掉线归一化为 EOF 这些都只在真实字节流上才成立。
